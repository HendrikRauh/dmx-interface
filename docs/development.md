We set up a Nix development shell with all the tools needed for the project. We recommend using it because it ensures a consistent environment across all developers and our CI pipeline.

## Setup

> [!NOTE]
> If you already have Nix installed you can skip this section.

If you're on Linux or macOS you can install the Nix package manager either via the [Determinate Systems installer](https://determinate.systems/nix-installer/)
(recommended) or the official [nixos.org installer](https://nixos.org/download/)
with `experimental-features = nix-command flakes` in `nix.conf`. Optionally you can install [direnv](https://direnv.net/) so the shell is entered
automatically every time you enter the project directory which is quite convenient.

> [!TIP]
> If you're on Windows we are currently setting up a devcontainer. We are currently working on it because usb pass-through is not straightforward. For now you could use [WSL](https://learn.microsoft.com/en-us/windows/wsl/) plus
> [usbipd-win](https://github.com/dorssel/usbipd-win) for USB pass-through or have a look at the [devcontainer branch](https://github.com/HendrikRauh/dmx-interface/tree/devcontainer).

Install [git-lfs](https://git-lfs.com/) as well: the case vendor parts under
`assets/case/parts/` are stored with it, and without the filter driver you get
pointer files instead of STEP models.

## Common tasks

We use [invoke](https://www.pyinvoke.org/) to run common tasks. Run `inv --list` for the full set (or read their definition in `tasks.py`). Here are some of the most common ones:

| Command | What |
| --- | --- |
| `inv build` | Debug build (bundles the web UI first) |
| `inv flash` | Build → merged image → flash via esptool |
| `inv monitor` | Open the serial monitor for logs over USB |
| `inv check` | Run [clippy](https://doc.rust-lang.org/clippy/) to check Rust code |
| `inv format` | Run all [pre-commit hooks](#pre-commit-hooks) on all files |
| `inv docs` | Build the documentation (pass `-o` to open it) |
| `inv docs:dev` | Start a local docs server with hot reload |
| `inv web:build` | UI production build |
| `inv web:dev` | UI dev server with mock API |
| `inv generate-case` | Render the [build123d case model](./case.md) to STL/STEP |

The **API reference** is generated by rustdoc and ships with the built site at
`/api/`. `inv docs:rustdoc` regenerates it on its own.

## CAD environment

`inv generate-case` runs `assets/case/src/main_case.py` through the Python
environment that `flake.nix` builds from `pyproject.toml` and `uv.lock`. Two
parts of that setup are load-bearing — both were hard to diagnose.

### `python` is pinned to 3.13 on purpose

`flake.nix` has exactly **one** `python` binding (`python = pkgs.python313;`)
and everything derives from it: `buildInputs` (`python`, `python.pkgs.invoke`,
`python.pkgs.pyserial`), `UV_PYTHON`, and the venv path inside
`LD_LIBRARY_PATH` (`${virtualenv}/lib/${python.libPrefix}/site-packages/vtkmodules` —
note the `lib/`, `libPrefix` alone is just `python3.13`). Do not "simplify" any
of these back to `pkgs.python3` — on current nixpkgs that is 3.14, and the
locked wheel stack is cp313-only:

- `cadquery-ocp` 7.8.1.1.post1 ships cp313-only manylinux wheels and **no
  sdist**, and the locked `build123d` 0.10 requires cadquery-ocp 7.8, so `uv`
  fails at lock time with `No compatible wheel, nor sdist found for package 'cadquery-ocp'`. `requires-python = ">=3.13,<3.14"` in `pyproject.toml` keeps
  that failure explicit instead of mysterious.
- Upstream now has cp314 wheels (cadquery-ocp 8.0, build123d 0.13), but that is
  a major bump, not a flake tweak: build123d ≥ 0.13 depends on
  `cadquery-ocp-novtk>=8.0` (a different, VTK-free package, which would drop
  the `vtkmodules` entry below), plus `ocp-vscode` 4.x and a port of
  `assets/case/src/main_case.py`.

The failure mode that cost the most time (reproduced twice): the nixpkgs
python setup hook puts a buildInput's `site-packages` on `PYTHONPATH` **only
when its interpreter version matches**. With nixpkgs `python3` = 3.14 and a
3.13 venv, `dmx-env` never reaches `PYTHONPATH` and
`python -c "import build123d"` dies with `ModuleNotFoundError` — while the
shell's `python` itself looks perfectly fine (`python -V` prints 3.14.x). On a
nixpkgs where `python3` is still 3.13 this works by accident.

Second trap, even with that bridge in place: bare `python` is **not**
guaranteed to be the pinned interpreter. `pre-commit-check.enabledPackages`
puts nixpkgs' python3 (3.14) and its hook packages on `PATH` _ahead_ of
`python313`, so `python` finds the pure-python package via `PYTHONPATH` and
then fails deep inside with `ModuleNotFoundError: No module named 'OCP.OCP'` —
a cp313 extension module is invisible to a 3.14 ABI. The `shellHook` therefore
prepends `${virtualenv}/bin` to `PATH`: the venv interpreter must lead, and
PATH order elsewhere is not to be trusted.

### Native libraries come from `LD_LIBRARY_PATH`

The venv is built from unpatchelf'ed manylinux wheels (`dontAutoPatchelf` for
cadquery-ocp), so OCP's ELF dependencies resolve only through
`LD_LIBRARY_PATH`; nix's `ld.so` consults the store's `ld.so.cache` and
**never** `/usr/lib`, so a working host toolchain does not leak in. Each entry
in `flake.nix` is load-bearing — every single one was removed and re-added
after an `ImportError`:

| `LD_LIBRARY_PATH` entry | Needed by | Error without it |
| --- | --- | --- |
| `stdenv.cc.cc.lib` | `OCP.so` links libstdc++ directly | `ImportError: libstdc++.so.6` |
| `expat` | OCCT STEP/IGES readers | `ImportError: libexpat.so.1` |
| `zlib` | OCCT | `ImportError: libz.so.1` |
| `libGL`, `libX11` | OCCT visualization (TKService / TKOpenGl) | `ImportError: libGL.so.1` |
| `…/site-packages/vtkmodules` | bundled VTK 9.3 (`libvtk*-9.3.so`) shipped _inside_ the cadquery-ocp wheel | `ImportError: libvtkWrappingPythonCore3.13-9.3.so` |

Do **not** substitute nixpkgs `vtk` or `occt` for the last row: nixpkgs ships
VTK 9.5 / OCCT 7.9 with different SONAMEs and cannot satisfy those `NEEDED`
entries. A nonexistent directory in `LD_LIBRARY_PATH` (such as an old
`site-packages/cadquery_vtk`) is silently ignored.

Sanity check after touching any of this:

```sh
nix develop -c python -c "import build123d, ocp_vscode"
```

## Pre-commit hooks

We use automated hooks that run before every commit to ensure we catch mistakes early. The hooks are configured in `flake.nix` via git-hooks.nix (do **not** edit
`.pre-commit-config.yaml`). They run tasks like rustfmt, taplo, oxlint/oxfmt,
alejandra/statix/deadnix, markdownlint + mdformat + cspell, shellcheck/shfmt,
ripsecrets, actionlint and convco.

Convco parses your commit message and blocks it if it does not follow the [conventional commit specification](https://www.conventionalcommits.org/).
